## 目的

今のアプリは、合言葉を知っている人なら誰でも、全員の予定とメモを書き換えられる。これを「自分の予定とメモだけ書き換えられる」形に変える。誰が操作したかが分かるようになるので、#2 のコメントやスタンプの送り手も決められる。

閲覧だけなら、今までどおり合言葉で入れる。

## 決定事項

- ログインはメールアドレスと PW。
- 登録時は、メールに送る 6桁のコードで本人確認をする。
- PW のリセットは、メールで送る 1回限りの URL で行う。
- 1アカウント = 1人（既存の `people` の1行）。登録時に「未紐付けの既存の人から選ぶ」か「新しく作る」を選ぶ。
- 紐付けは先着。紐付けの解除と管理者は作らない。
- 鍵ロックは残す。ログイン済みの人だけが解除できる。ログイン直後はロックから始まる。
- 部屋のメモ（`person_id` が null）は、ログイン済みなら誰でも編集・削除できる。
- 人に紐付いた在室とメモは、その人のアカウントだけが編集・削除できる。
- アカウントのない人は認めない。「＋ 人を追加」は廃止する。紐付け前の既存の人は閲覧のみ。
- 合言葉は最初の関門のまま。登録画面とログイン画面も、合言葉を通った後に出す。合言葉を持たない端末でメールのリセットリンクを開いても、合言葉のあとにそのリンクへ戻れる（下の「ログイン前（合言葉だけ）」）。
- 方式は「セッション表 + nodemailer」。

## データ

既存の `people`, `stays`, `memos` は変えない。起動時に次のテーブルを `CREATE TABLE IF NOT EXISTS` で追加する。既存の人は全員、紐付け前から始まる。`pending_signups` に `resend_count`・`browser_hash` を足す前の DB（開発中に作られたもの）は、起動時に `PRAGMA table_info` で列の有無を調べ、なければ `ALTER TABLE ... ADD COLUMN` で足す（何度起動しても同じ結果になる）。`browser_hash` の索引は、列を足したあとに作る。足す前の行の `browser_hash` は NULL のままで、どの Cookie とも合わないので確認できず、期限（10分）で消える。

SQLite は、外部キーを有効にし（`foreign_keys = ON`）、`busy_timeout` を 5000ミリ秒にして開く。起動直後の書き込み（期限切れの行の掃除など）が、他の接続の書き込みと重なって `database is locked` で落ちないようにするため。

- `users`: `id`, `email`（小文字化・一意）, `password_hash`, `person_id`（一意。`people` への外部キー。`ON DELETE CASCADE`）, `created_at`
- `sessions`: `token_hash`（主キー）, `user_id`（`ON DELETE CASCADE`）, `expires_at`
- `pending_signups`: `email`（主キー）, `password_hash`, `person_id`（選んだ既存の人。新規なら null）, `new_name`, `new_color`, `code_hash`, `expires_at`, `attempts`（間違いの回数）, `sent_at`, `resend_count`（再送した回数。新しい行は 0）, `browser_hash`（申し込んだブラウザに渡したトークンの SHA-256。索引つき。NULL でもよい）
- `reset_tokens`: `token_hash`（主キー）, `user_id`（`ON DELETE CASCADE`）, `expires_at`, `used_at`

### 値の作り方

- PW は `crypto.scrypt`（ソルト 16バイト、鍵長 64バイト）でハッシュする。`scrypt$N$r$p$salt$hash` の形で保存する。比較は `crypto.timingSafeEqual`。
- PW は 8文字以上 128文字以下。メールは 254文字以下で、簡単な形式検査だけする。空白と、アドレスの書式に使う記号（`< > ( ) , ; : " [ ] \`）は入れられない（`victim<attacker@evil.com>` のように、別のアドレスを紛れ込ませた宛先を作らせないため）。
- セッションのトークンは `crypto.randomBytes(32)` の base64url。DB には SHA-256 の hash だけを保存する。有効期間は 30日で、使うと延ばす（延ばすのは 1日に 1回まで）。
- 6桁コードは `crypto.randomInt` で作る。DB には hash だけを保存する。
- リセットのトークンは `crypto.randomBytes(32)` の base64url。DB には hash だけを保存する。
- 登録の申し込みを結び付けるブラウザのトークンも、`crypto.randomBytes(32)` の base64url。Cookie に渡し、DB には SHA-256 の hash（`browser_hash`）だけを保存する。

## 認証の流れ

### 登録

1. `POST /api/auth/signup`: メール、PW、人の選択（既存の `person_id`、または新規の名前と色）を送る。
   - メールがすでに `users` にあれば「このメールアドレスは登録済みです」を返す。
   - 選んだ既存の人がすでに紐付け済みなら、エラーを返す。
   - 入力の型も検査する（メール、PW、名前、色は文字列。`person_id` は整数）。違えば `400` を返す。
   - 同じメールの `pending_signups` が、期限内のまま残っているときは、上書きしない。第三者が上書きして、確認待ちの登録のパスワードや紐付けをすり替えられないようにするため。メールも送らない。ただし、その行を作ったブラウザ自身（Cookie `iruinai_signup` の hash が、行の `browser_hash` と合うもの）からの申し込みは `{ ok: true, resumed: true }` を返す（戻るボタンや再読み込みで行き詰まらないため。下の「申し込んだブラウザへの結び付け」）。それ以外は、前回の送信から 60秒以内なら `429`（確認メールを送ったばかり）、それより後なら `400`（「このメールアドレスは、すでに登録の手続き中です。自分で申し込んだ場合は、申し込んだブラウザで、届いた確認コードを入力してください。別のブラウザで申し込んだ場合や、心当たりがない場合は、10分ほど待ってからやり直してください」）を返す。申し込んだ覚えのない人に、他人が始めた登録のコードを入力するよう誘わない文面にする。コードを送り直したいときは `resend` を使う。
   - 6桁コードをメールで送る。有効期間は 10分。ここまでの検査を通った要求だけが、メール送信の上限（下の「メール送信の上限」）に数えられる。上限を超えていれば `429` を返し、`pending_signups` の行も作らず、メールも送らない。送信に失敗したら「メールを送れませんでした」（`502`）を返し、`pending_signups` は作らない。
   - 行を作ってメールを送れたときだけ、申し込んだブラウザに Cookie `iruinai_signup` を渡し、行の `browser_hash` にそのトークンの hash を入れる（下の「申し込んだブラウザへの結び付け」）。応答は `{ ok: true }`。
2. `POST /api/auth/verify`: 6桁コードだけを送る（`{ code }`）。メールもパスワードも要らない。本文に `email` や `password` があっても読まない。
   - どの確認待ちを確認するかは、Cookie `iruinai_signup` の hash が `browser_hash` と合う行だけで決める。Cookie がない・合う行がないときは、何も数えずに `400`（「確認の手続きが見つかりません。もう一度、登録から始めてください」。応答にはほかに `noPending: true` を付ける。画面が文面を比べずに、登録の画面へ戻すため）を返す。行が期限切れなら、行を消し、Cookie も消して、「コードの有効期限が切れました。もう一度登録してください」（`400`）を返す。
   - コードの比較は `crypto.timingSafeEqual` で行い、6桁の数字でなければ不一致とする（`code` がない・文字列でないときも `400` の不一致で、500 にはしない）。違えば「確認コードが違います（あと N 回）」を返す。
   - 間違いは、確認待ちの行ごとに 5回までで、5回目に間違えると、その行は使えなくなる（正しいコードを入れても通らない。「間違いが続いたため、このコードは使えません。10分ほど待ってから、もう一度登録してください」）。このとき `pending_signups` は消さず、期限まで残す。消してしまうと、すぐに登録し直してメールを送らせられるので、再送の 60秒の制限をすり抜けられるため。間違いの回数はコードを送り直しても戻らない。
   - 予期しないエラー（DB のエラーなど）は、内容を返さず「サーバーでエラーが起きました」（`500`）とだけ返し、元のエラーはサーバーのログに出す。
   - 正しければ、1つのトランザクションで次を行う。紐付け先をもう一度確認する（先に取られていたらエラー。このときは `pending_signups` を消し、`iruinai_signup` の Cookie も消して、選び直してすぐ登録し直せるようにする）。新規なら `people` を作る。`users` を作る（パスワードは、申し込みのときに保存した hash をそのまま使う）。`pending_signups` を消す。
   - 続けてセッションを作り、Cookie を返す（そのままログイン状態になる）。`iruinai_signup` の Cookie は、同じ Path で `Max-Age=0` にして消す。
3. `POST /api/auth/resend`: コードを再送する。本文は要らない（`email` があっても読まない）。対象は verify と同じく Cookie の行だけで、Cookie がない・合う行がない・期限切れのときは、verify と同じ `400`（「確認の手続きが見つかりません。もう一度、登録から始めてください」）を返す。そのあと、次のとおり、上から順に調べる。
   - 間違いの回数が 5回に達した行（ロック中）は、ロックの案内（`400`）を返し、メールを送らない。再送しても間違いの回数は戻さない。戻すと、1分ごとに 5回ずつ当てずっぽうを試せるため。
   - 再送は 1つの行につき 3回まで。4回目は「再送できる回数の上限です。10分ほど待ってから、もう一度登録してください」（`429`）を返し、メールを送らない。
   - 前回の送信から 60秒以内は拒否する（`429`）。
   - 通れば（ここまでの検査はすべてメールを送らない拒否なので、上限には数えない）、メール送信の上限に数える。上限を超えていれば `429` を返し、予約も書かず、メールも送らない。
   - 上限の内側なら、新しいコードに差し替え、有効期間を今から 10分にし、`sent_at` と `resend_count` を更新する。ここまでをメールを送る前に DB へ書く（予約）ので、続けて届いた 2つ目のリクエスト（二重クリックなど）は 60秒の判定で止まり、メールは 1通だけになる。メールの送信に失敗したら（`502`）、予約を元に戻す（コード、期限、`sent_at`、`resend_count`。間違いの回数は触らない）。メールが届かないまま 1分待たされたり、再送の回数だけ減ったりしないようにするため。
4. `GET /api/auth/pending`: 申し込んだブラウザの確認待ちを返す。画面を開き直したあとに、コード入力の画面へ戻るために使う。合言葉の内側にあり、`Cache-Control: no-store` を付ける。Cookie の hash が合う、期限内の行があれば `{ pending: { email, expires_at, resend_available_at, locked } }`（時刻は UNIX ミリ秒。`resend_available_at` は `sent_at` の 60秒後、`locked` は間違いが 5回に達しているか）、そうでなければ `{ pending: null }`。Cookie がなければ何も見せない（メールアドレスも漏らさない）。
5. 期限切れの `pending_signups` は、登録の申し込み、ログインの成功、サーバーの起動のときにまとめて消す。`verify` と `resend` は、期限が切れた行を見つけたら無効として扱う。

### 申し込んだブラウザへの結び付け

登録の確認待ちは、申し込みの画面を送ったブラウザに結び付ける。確認コードの画面は、メールもパスワードも尋ねず、コードだけを受け取る。

- Cookie `iruinai_signup`: 値は `crypto.randomBytes(32)` の base64url。属性は `HttpOnly; SameSite=Lax; Path=/api/auth; Max-Age=3600`（1時間）で、HTTPS のとき（セッション Cookie と同じ判定）は `Secure` を付ける。`Path=/api/auth` なので、ほかの API には送られない。行の有効期間（10分）より長いのは、再送で期限が延びてもブラウザ側が先に切れないようにするため。
- 申し込みに成功するたびに新しいトークンを作り、行の `browser_hash` に hash を入れ、Cookie を渡す。同じブラウザの前の `iruinai_signup` は置き換わる（前の確認待ちは、そのブラウザからは確認できなくなり、10分で消える）。メールを送れなかったとき、入力の誤り・上限超えなど、行を作らなかった申し込みには Cookie を付けない。
- 確認・再送・`pending` は、本文のメールではなく、この Cookie の hash で行を引く。
- 同じブラウザからの同じメールの申し込み直し（`resumed`）は、メールを送らず、メール送信の上限にも、行の数（`attempts`・`resend_count`・`sent_at`・コード）にも触れない。申し込みの内容（パスワード・人の選択）も書き換えない。書き換えるには scrypt が要るので、Cookie を持っていれば何度でも CPU を使わせられてしまうため。変えたいときは、期限（10分）を待つか、登録したあとにパスワードを再設定する。
- 守るもの: 他人（例: 同じ部屋の人）が被害者のメールアドレスと自分のパスワードで登録を始め、被害者に届いたコードを入力させて、攻撃者がパスワードを知っているアカウントに被害者を入らせる、という乗っ取り（pre-hijacking）。Cookie は申し込んだブラウザにしかないので、被害者が自分の受信箱のコードを自分のブラウザに入れても、行が見つからず確認できない（間違いの回数も増えない）。これは、以前 `verify` に求めていたパスワードの代わりの守り。
- 代わりに、確認コードは申し込んだブラウザでしか入力できない（別の端末・別のブラウザ・Cookie を消したあとは、10分待って申し込み直す）。申し込み直しは、別のブラウザからは `429`/`400` で断られる。
- 残る前提: 攻撃者が被害者のブラウザに Cookie を直接入れられる場合（同じサイトの兄弟のサブドメインや、HTTP の通信路を書き換えられる場合）は防げない。HTTP のままの運用は、もともと README で HTTPS を求めている。トークンは 256ビットのランダムな値で、推測はできない。

### ログイン

- `POST /api/auth/login`: メールと PW を送る。失敗が続いた場合の制限は、合言葉と似た方式にする。同じ IP から 5回続けて失敗すると、最後の失敗から 1分間は `429` を返す（この間は、正しい PW でも通さない）。合言葉と違い、ログインに成功しても失敗の回数は戻さない。自分のアカウントで成功を挟んで、他人のアカウントへの総当たりの回数を戻されないようにするため。回数は、最後の失敗から 1分たつと自然に切れる。
- 成功したらセッションを作り、Cookie を返す。

### PW リセット

- `POST /api/auth/forgot`: メールを送る。登録の有無にかかわらず、同じ応答「送りました」を返す。登録済みのときだけ、メールを送る。
  - リセット URL は `<公開URL>/reset?token=<トークン>`。有効期間は 1時間。
  - 同じ人の古い未使用トークンは無効にする。
  - 同じメールへの送信は 60秒に 1回まで。それより早い要求にも同じ応答を返すが、メールは送らない（メール爆撃の防止）。
  - 書式が正しい要求は、宛先が登録済みかどうかにかかわらず、すべてメール送信の上限に数える（登録の有無を、上限の減り方から知られないため）。上限を超えたときは、宛先が登録済みでも未登録でも同じ `429` を返す（本文も同じ）。書式が正しくない要求は、メールを送る元になりえないので数えず、今までどおり `{ ok: true }` を返す。
  - `SMTP_HOST` が設定されていて、`PUBLIC_URL` が未設定のときは、メールを送らない。応答は同じ `{ ok: true }` のまま、サーバーのログにその理由を出す。`Host` ヘッダーは相手が好きに書けるので、それで URL を作ると、本物のメールに偽のドメインへのリンクを入れさせられるため。
- `POST /api/auth/reset`: トークンと新しい PW を送る。
  - 期限内で未使用のときだけ受け付け、`used_at` を記録する。同じトークンは二度と使えない。
  - PW を更新し、その人のセッションをすべて消す。

### メール送信の上限

`signup`・`resend`・`forgot` はメールを送るので、メール爆撃や SMTP の送信枠の使い切りを防ぐため、サーバーのメモリ上で次の上限を数える（再起動すると 0 に戻る）。

- 同じ IP（`req.ip`）から 1時間に 10回まで。3つの API の合計。
- 全体で 1時間に 100回まで。
- 回数は、通数ではなく要求の数（`forgot` は宛先が未登録でも数えるため）。IP ごとの窓も全体と同じ 1時間にする。
- 超えた要求には `429`（「送信の回数が多すぎます。しばらくしてからやり直してください」）を返し、メールも行も作らない。
- 数えるのは、メールを送るところまで進んだ要求だけ。入力の誤り、登録済み、確認待ち、再送の間隔や回数の制限、ロックなど、送らずに終わる拒否は数えない。`forgot` だけは、上の「PW リセット」のとおり、書式が正しければ全部数える。
- 数えた要求の送信に失敗しても、数えたまま（送ろうとしたため）。
- 記録は送った時刻の配列で、上限に達したら足さないので、上限より長くならない。IP ごとの記録は 1時間ごとにまとめて捨てる。
- 上限は環境変数 `MAIL_IP_LIMIT`（既定 10）と `MAIL_GLOBAL_LIMIT`（既定 100）で変えられる。テストでは小さい値にする。受け付けるのは 1以上の10進の整数だけで、設定してあるのに使えない値（0・負の数・文字・`0x10`・`1e3` など。0 は「無効」ではない）は、既定の値を使い、起動時に警告を出す。`MAIL_IP_LIMIT` が `MAIL_GLOBAL_LIMIT` 以上のときも、IP ごとの上限が働かないので、起動時に警告を出す。
- IP ごとの上限が全体より小さく、窓も同じなので、1つの IP が全体の上限を使い切ることはできない（使い切るには複数の IP が要る）。全体の上限を使い切られると、最大 1時間は誰の登録もリセットも止まる。
- 注意: リバースプロキシの後ろ（`trust proxy` なし）では、IP がプロキシのものになるので、全員が 1つの IP として数えられ、IP の上限（1時間に 10回）を全員で分け合う（ログインの失敗回数と同じ制約）。

### セッション

- Cookie 名は `iruinai_session`。属性は `HttpOnly; SameSite=Lax; Path=/` で、HTTPS のときは `Secure` を付ける。HTTPS かどうかは、`req.secure` が真であるか、`PUBLIC_URL` が `https://` で始まるかで判定する。TLS を終端するプロキシの後ろでは、アプリには HTTP で届き `req.secure` が偽になるため、`PUBLIC_URL` も見る。
- `GET /api/me` は、ログイン中なら `{ user: { id, email, person_id } }`、そうでなければ `{ user: null }` を返す。
- `POST /api/auth/logout` は、そのセッションだけを消す。
- 既存の `GET /logout`（合言葉のログアウト）は、合言葉の Cookie とセッションの行・Cookie を両方消して `/login` へ送る。`ROOM_PASSWORD` を設定したときだけ存在し、合言葉の門より前に置く（合言葉を持たない端末でも、Cookie を消せる）。
  - 他のサイトのリンクや画像で勝手にログアウトさせられないよう（`SameSite=Lax` の Cookie は、他サイトからのリンクの移動には付くため）、GET は `Sec-Fetch-Site` が `same-origin` か `none`（アドレス欄、ブックマーク、同じサイトのリンク）のときだけ実行する。`cross-site`、`same-site`（兄弟のサブドメインも他サイトと同じに扱う）、ヘッダーなしのときは、「ログアウトしますか？」の確認画面（`public/logout.html`。`/style.css` は合言葉の内側にあり、合言葉のない端末では読めないので、見た目はページの中に書く。ユーザーの情報は入れない）を `200` で返し、ボタン（`POST /logout`）が押されたときだけ実行する。
  - `POST /logout` は、同じ処理を行って `/login` へ `303` で送る。ヘッダーのないクライアント（curl など）は、そのまま実行する。`Sec-Fetch-Site` が `same-origin` 以外のブラウザからの POST（他サイトのフォームの自動送信）は実行せず、確認画面を返す。
  - 画面のヘッダーの「ログアウト」ボタンは、これとは別に `POST /api/auth/logout`（セッションだけを消す）を使う。

### 退会

- `POST /api/me/withdraw`: PW を送る。正しければ、自分の人（在室とメモごと）、アカウント、セッションを削除する。元に戻すことはできない。
- 退会の PW にも、ログインと同じ制限を付ける。セッションを持っている相手が PW を当てに来られるうえ、1回ごとに scrypt を走らせるため。同じユーザーが 5回続けて間違えると、最後の間違いから 1分間は `429`（「間違いが続いたので、1分ほど待ってからもう一度どうぞ」）を返す。この間は正しい PW でも通さず、PW も調べない。数えるキーはユーザー ID（IP ではない）なので、他のユーザーには影響しない。成功しても回数は戻さない（成功すればアカウントごと消える）。回数は最後の間違いから 1分で数え直す。
- `DELETE /api/people/:id` は廃止する。
- 削除したアイコン画像は、今までどおり次の起動時にまとめて消える。

## 権限（サーバーで強制）

セッションを読むミドルウェアを、合言葉の検査の後、API ルートの前に置く。GET は今までどおり、合言葉を通れば見られる。`/api/auth/*` 以外の POST/PUT/DELETE は、未ログインなら `401 {"error":"ログインしてください","needLogin":true}` を返す。`needLogin` は、合言葉の `401` と見分けるための印で、画面は `needLogin` がない `401` のときだけ合言葉の画面へ移す。

`lib/guard.js` に所有者の検査をまとめる。「自分の人」とは、`req.user.person_id` のこと。

- **在室（`stays`）**:
  - 追加・変更・削除は、自分の `person_id` のものだけ。
  - `PUT` は、変更前の行と変更後の `person_id` の両方が自分でなければならない。
  - `batch`, `import`, `remove`, `restore` は全件を検査する。他人のものが 1件でもあれば、何も実行せず `403` を返す。
  - `restore` は、同じ `id` の既存の行が他人のものでないことも確認する。また、これまでに採番されていない大きな `id` は拒否する（次の追加が採番できなくなって壊れるため）。
- **メモ（`memos`）**:
  - `person_id` が null（部屋）のメモは、ログイン済みなら誰でも編集・削除できる。
  - 人のメモは、その人のアカウントだけが操作できる。
  - `PUT` は、変更前の行と変更後の対象（自分の人、または部屋）の両方を検査する。他人の人への付け替えは `403`。
  - `batch`, `remove`, `restore` は在室と同じく全件を検査する。
  - `restore` は在室と同じく、これまでに採番されていない大きな `id` を拒否する。
- **人（`people`）**:
  - `POST /api/people` は廃止する。人は登録時にだけ作る。
  - `PUT /api/people/:id` は本人だけ。
  - `POST /api/people/restore` は、変更の取り消しにだけ使う。今ある自分の人だけを対象にし、リクエストの `stays` と `memos` は受け付けない。削除済みの人を作り直す機能は外す。他の人が使っているアイコン画像は取り込まない（起動時の縮小で元の画像が消え、その人のアイコンが壊れるため）。
- **`GET /api/people`**: 各行に `claimed`（0/1）を足す。登録画面の「選べる人」に使う。メールアドレスは返さない。

CSRF 対策は、Cookie の `SameSite=Lax` に任せる。他サイトからの POST には Cookie が付かない。

## 画面

### ログイン前（合言葉だけ）

- 合言葉の門は、GET のページ（`/`, `/index.html`, `/account`, `/reset`）を合言葉の画面へ送るとき、元の道とクエリを `next` に控える（`/login?next=%2Freset%3Ftoken%3D…`）。API（`401`）、画像・スクリプトなどの素材、GET 以外には付けない。`/` だけのときも付けない。合言葉の画面はこの値を、HTML に escape した隠し欄（`<input type="hidden" name="next">`）に入れ直し、合言葉が合ったら `303` でそこへ送る。間違えたときや待ち時間の案内（`e=wrong` / `e=wait`）でも、`next` を引き継ぐ。
- `next` として使えるのは、このサイトの中の道だけ。次のどれかに当てはまる値は捨てて、`/` へ送る（合言葉の判定には影響しない）: 先頭が `/` でない、2文字目が `/` か `\`、`\` か `://` を含む、制御文字（`%0d%0a` のように `%` で書いたものを含む）を含む、2000文字を超える、`/login` か `/logout`（大文字小文字・末尾の `/` の違いを含む）自身。ブラウザが直して開く道（`/./logout`・`/%2e/logout`・`/a/../logout` など）も、`new URL` で直した道で調べて同じ扱いにし、直した道が `//` で始まるものも捨てる（返すのは元の値のままで、直した道は返さない。`/..//evil.com` が `//evil.com` になるため）。`/login`・`/logout` を捨てるのは、ループと、意図しないログアウトを避けるため。
- ヘッダーに「ログイン」ボタンを出す。鍵を押すと「ログインすると編集できます」と出し、ログイン画面へ誘導する。
- 予定とメモは見られる。ドラッグ、追加ボタン、`i` のキーボードモードは使えない。

### 新しい画面 `public/account.html`

合言葉の後に出す。`/account` と `/reset` で配信し、`style.css` を使う。1ページ内で次の表示を切り替える。

- ログイン: メールと PW。「PW を忘れた」「新規登録」へのリンクを付ける。
- 新規登録: メール、PW、PW 確認。人は「未紐付けから選ぶ」か「新しく作る（名前と色）」。新規のアイコンは、登録後に人の編集画面で設定する。
- コード入力: 6桁のコードの欄だけ（メールもパスワードも尋ねない）。画面には、コードを送ったメールアドレスの案内（文字として出す）、「登録する」、再送ボタン（60秒のカウントダウンつき）、登録の画面へ戻る「入力し直す」だけを置く。画面は何も覚えず、ブラウザの保存領域も使わない。ページを開いたときに `GET /api/auth/pending` を呼び、確認待ちがあれば（メールのリセットリンクの `?token=` があるときを除いて）この画面を直接出す。案内には `pending.email`、再送のカウントダウンには `resend_available_at`（0〜60秒に収める）を使い、`locked` なら「間違いが続いたため…」を出す。申し込みの応答が `resumed: true` のときも、同じ `pending` から表示する。`verify` や `resend` が「確認の手続きが見つかりません」（`noPending`）を返したら、登録の画面に戻してその文面を見せる。コード入力の画面へ行くのは、申し込んだ直後と、ページを開き直したときだけ（登録の画面にリンクはない）。
- PW リセット要求: メールを入力する。
- 新しい PW の入力: `/reset?token=…` から開く。PW を 2回入力する。完了するとログイン画面へ移る。

### ログイン後

- ログイン直後は、ロックから始まる。鍵を押すと編集できる。5分で自動ロックする仕組みも今までどおり。
- ヘッダーの「＋ 追加」（人の追加）は消す。「…」メニューに「ログアウト」を入れる。
- 人の編集（名前、色、アイコン）は、自分の人の鉛筆アイコンだけ出す。ダイアログの「削除」は「退会」に変え、PW を再入力させる。元に戻せないことも明記する。
- 在室とメモの「だれ」は、自分の人に固定する。キーボードモードも、人の選択画面を飛ばして自分で始める。`p` キーは無効にする。
- 他人の予定とメモは、ロック解除中でも閲覧ダイアログで見るだけにする。ドラッグとリサイズもできない。
- CSV の取り込みは、自分の人に対してだけ行う。

画面の制限はあくまで案内で、実際の制限は「権限」の節のサーバー側の検査で行う。

## 設定（`.env`）

- 起動時に `process.loadEnvFile()` で `.env` を読む。ファイルがなければ何もしない。すでに設定されている環境変数は上書きしない。読むファイルは `ENV_FILE` で変えられる（テスト用）。`.env` は `.gitignore` 済み。`.env.example` を追加する。
- 変数: `SMTP_HOST`, `SMTP_PORT`（既定 587）, `SMTP_USER`, `SMTP_PASS`, `SMTP_SECURE`（465 のとき `true`）, `MAIL_FROM`。
- メール送信の上限の変数: `MAIL_IP_LIMIT`（既定 10）, `MAIL_GLOBAL_LIMIT`（既定 100）。
- `SMTP_HOST` が未設定なら、メールは送らず、コードとリセット URL をサーバーのコンソールに出す。LAN 内での簡易運用とテスト用。起動時に「メール: コンソール出力」と表示する。
- リセット URL は、`PUBLIC_URL`（既存の変数）から組み立てる。`SMTP_HOST` が設定されているときは、`PUBLIC_URL` が必須になる。未設定なら、`Host` ヘッダーは偽造される恐れがあるので URL を作らず、パスワード再設定のメールを送らない（ログに理由を出す。API の応答は変わらない）。起動時にも警告を出し、README で `PUBLIC_URL` の設定を求める。`SMTP_HOST` が未設定（コンソール出力）のときは、URL をサーバーのコンソールに出すだけなので、`PUBLIC_URL` が未設定なら `Host` ヘッダーから組み立てる。
- `MAIL_FROM` が未設定なら、送信元は `SMTP_USER` にする。
- `APP_TITLE`: アプリの名前（既定は「在室カレンダー」）。左上の見出し、タブのタイトル、共有時のタイトル（`og:site_name`・`og:title`）、合言葉・アカウント・ログアウト確認の画面、確認コードとパスワード再設定のメールの件名（`【名前】確認コード`・`【名前】パスワードの再設定`）と確認コードの本文（`名前の確認コードです。`）に使う。
  - `lib/appTitle.js` の `appTitle()` が、呼ばれるたびに `process.env.APP_TITLE` を読む（`server.js` が `.env` を読んだあとの値を、読み込みの順番に頼らず使うため）。前後の空白を取り、空白・改行（CR/LF を含む）・制御文字の連なりを 1つの空白にし、40文字（コードポイント）で切る。空になったら既定の名前。1行にするのは、メールの件名に改行を入れさせないため。
  - 画面（`index.html`・`login.html`・`account.html`・`logout.html`）には、プレースホルダー `__TITLE__` を置き、`sendPage` が `escapeHtml(appTitle())`（`& < > " '` を escape）で置き換える。置き換えは 1回の走査で、値の中の `$&` や `__NEXT__` のような文字は特別に扱わない。`/account.html`・`/login.html`・`/logout.html` のように `.html` のアドレスで開かれたときも、静的ファイルとして生のまま配らず、同じ処理を通す。メールには escape しない値をそのまま入れる。
  - 起動のログ `在室カレンダー: http://localhost:PORT` は変えない（テストの起動待ちや運用の目印に使う）。
  - 共有時の画像 `public/iruinai-ogp.png` は静的な画像で、既定の名前が焼き込まれている。`APP_TITLE` には追従しない（README に書く）。
- `ROOM_PASSWORD` が未設定なら、LAN につながる人なら誰でも登録できる。README の注意事項に書く。

## エラーの扱い

- 入力の不正は `400`、未ログインは `401`、他人のものへの操作は `403`、トークン切れやコード違いは `400`、短い間隔での繰り返しは `429`。メッセージは日本語で返す。
- メール送信の失敗は、登録の途中データを作らずに「メールを送れませんでした」（`502`）と返す。
- 総当たりの制限は、画面ごとに違う。
  - ログイン: 同じ IP からの失敗回数（5回続けて失敗すると 1分間 `429`）。
  - 退会: 同じユーザーの PW の間違い回数（5回続けて間違えると 1分間 `429`。上の「退会」と同じ）。
  - 登録（`signup` と `verify`、`resend`）: 間違いの回数は IP ごとには数えない。確認待ちの行ごとに、コードの間違いは 5回まで（再送でも戻さない）、再送は 3回まで、再送の間隔は 60秒、有効期間は 10分。
  - メールを送る要求（`signup`・`resend`・`forgot`）: IP ごと（1時間に 10回）と全体（1時間に 100回）の上限。上の「メール送信の上限」。
- 予期しない例外は、内容（英語や SQLite のメッセージなど）をそのまま返さない。「サーバーでエラーが起きました」（`500`）を返し、元のエラーはサーバーのログに出す。壊れた JSON などリクエストの形そのものの誤りは「送信内容が正しくありません」（`400`）を返す。画像のアップロード（`PUT /api/people/:id`）は、2MB を超えると「画像は2MBまでです」（`400`）、それ以外の受け取りの誤り（壊れた multipart の `Unexpected end of form`・`Malformed part header`・`Multipart: Boundary not found`、許していない欄名など）は「アップロードの内容が正しくありません」（`400`）を返す。どちらもスタックはログに出さない。保存先に書けないなどサーバー側の問題（システムエラー）は、他の予期しない例外と同じく `500` のままログに残す。コードの中で意図して投げた入力エラーは、そのままの文面を返す。
- 登録の画面は「登録済みです」と答えるので、メールアドレスが登録済みかどうかが分かる。3〜4人の小さな部屋で、合言葉の内側にいる人だけが見る画面なので、これは許容する。PW リセットの画面は、登録の有無が分からない応答にする。

## テスト

もともとテストがなかったので、`node:test` で `npm test` を作った（依存の追加なし）。

- テストは `server.js` を子プロセスで起動する。一時の `DATA_DIR` と空きポートを使い、本番の `data/` には触れない。SMTP は未設定にして、コンソールに出たコードと URL を読み取る。「1分たつと戻る」のような時間の確認は、待たずに済むよう、子プロセスの `Date.now()` を進める `test/fake-clock.js`（`NODE_OPTIONS=--require`）を使う。製品のコードには何も足していない。
- 確認する項目:
  - 登録 → コード → ログインの一連の流れ
  - コードを 5回間違えると無効になる
  - 再送しても間違いの回数は戻らない。ロック中の再送はメールを送らない。再送は 3回まで。二重送信でメールは 1通だけで、送信に失敗したら予約を戻す
  - 確認待ちは申し込んだブラウザ（Cookie）に結び付く。被害者のメールで他人が始めた登録を、Cookie のない被害者が、コードが合っていても確認も再送もできず、間違いの回数も増えない。2つのメールの確認待ちは、それぞれの Cookie でだけ確認できる
  - 同じブラウザの申し込み直し（`resumed`）はメールも数も動かさない。別のブラウザは `429`/`400`
  - `GET /api/auth/pending`（Cookie なしは `null`、あれば自分の分だけ）
  - Cookie の属性（`HttpOnly`・`SameSite=Lax`・`Path=/api/auth`・`Max-Age`・HTTPS で `Secure`）と、確認後に消えること。DB には hash だけが入る
  - メールの書式に使う記号を含むアドレス、型が違う入力は `400`
  - 古い形式の DB（`resend_count`・`browser_hash` なし）でも起動できる
  - `APP_TITLE`: 見出し・タイトル・共有時のタイトル・合言葉/アカウント/ログアウトの画面・メールの件名と本文に出る。HTML の記号は escape される。改行は 1行にまとまり、100文字は 40文字に切れる。未設定・空白だけは既定。`.env` でも使える
  - リセット URL は 1回限りで、使うとその人の全セッションが消える
  - 他人の在室への PUT/DELETE/batch/restore が `403`
  - 他人の人への付け替えが `403`
  - 部屋のメモは、ログイン済みなら誰でも編集できる
  - 未ログインの書き込みは `401`
  - 紐付け済みの人を二重に選べない
  - 退会で人、在室、メモ、アカウントが消える
  - 退会のパスワードを 5回間違えると 1分間 `429`（正しいパスワードでも通さない）。1分たつと戻る。他のユーザーには影響しない
  - ログインの失敗のロックが、1分たつと解ける
  - メールを送る API の上限（IP ごと・全体、どちらも 1時間で戻る。IP ごとの分離、使えない設定値の警告を含む）。送らずに終わる拒否は数えない。`forgot` は登録の有無で応答が変わらない
  - `GET /logout` は `Sec-Fetch-Site` が `same-origin`・`none` のときだけ実行し、それ以外は確認画面。`POST /logout` で実行する
  - 合言葉のあと、元のページ（`next`）へ戻る。外部サイトなど安全でない値は `/` へ
  - 壊れた multipart は `400`（500 にしない）
