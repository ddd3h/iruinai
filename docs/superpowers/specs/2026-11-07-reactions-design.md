# 反応（スタンプ・コメント・通知）設計

日付: 2026-11-07
対象: issue #8 のサブプロジェクト2。サブプロジェクト1（アカウント基盤、`2026-11-06-user-accounts-design.md`）の上に作る。

## 目的

部屋にいる人どうしが、予定やメモに軽く反応できるようにする。スタンプとひとこと（コメント）を付けると、持ち主のカレンダーに丸い吹き出しが出て、右上のベルに履歴が残る。堅い連絡ではなく、「見たよ」「ありがとう」を気軽に伝える道具にする。

## 前提（アカウント基盤で決まっていること）

- 書き込みはログイン必須。合言葉だけの人は見るだけ。未ログインの書き込みは 401 `{needLogin:true}` を返す。
- 人（`people`）とアカウント（`users`）は 1 対 1。予定（`stays`）とメモ（`memos`）は `person_id` で持ち主が決まる。`person_id` が NULL のメモは「部屋のメモ」で、持ち主がいない。
- 汎用の Express エラー処理は、日本語の一般的な 500 文言を返し、`InputError` と `UserError` だけを通す。

## スコープ

### 入れるもの

- 予定とメモに付けるスタンプ（6 種）。
- 予定とメモに付けるコメント（40 字まで）。
- 反応が付いた予定の上に出る、新着のときだけの吹き出しと、短い「ぽん」という音（ミュート切り替え付き）。
- 右上のベルボタン、未読数、反応の履歴。
- 月表示の予定に出す反応数の小さな表示。
- 予定ダイアログ内の反応欄（スタンプ一覧・コメント欄・これまでの反応）。
- Codex が作るスタンプ画像を差し込める作り（画像がなければ内蔵イラスト）。必要な画像の一覧と生成用の指示文を `docs/stamps.md` に置く。

### 入れないもの

好きな絵文字、返信のつながり、コメントの編集、メール通知、プッシュ通知、リアルタイム通信（WebSocket・SSE）、反応への反応。

## 権限

- 反応を付けられるのはログイン中の人だけ。閲覧だけの人は一覧を見られる。
- 自分の予定・メモには付けられない（400 `自分の予定には反応できません`）。部屋のメモには誰でも付けられるが、持ち主がいないので通知は作らない。
- 持ち主のいない人（未登録の人）の予定にも付けられる。通知を受ける人がいないので、通知は作らない。
- 反応（スタンプもコメントも）を消せるのは、した本人だけ。対象の持ち主でも、他の人の反応は消せない（403 `他の人の反応は消せません`）。
- 退会すると、その人が付けた反応はすべて消える（`user_id` の外部キーで連鎖削除）。

## データ

```sql
CREATE TABLE IF NOT EXISTS reactions (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  stay_id INTEGER REFERENCES stays(id) ON DELETE CASCADE,
  memo_id INTEGER REFERENCES memos(id) ON DELETE CASCADE,
  stamp TEXT,            -- スタンプなら ID、コメントなら NULL
  body TEXT,             -- コメントなら本文、スタンプなら NULL
  created_at INTEGER NOT NULL,
  CHECK ((stay_id IS NULL) <> (memo_id IS NULL)),
  CHECK ((stamp IS NULL) <> (body IS NULL))
);
CREATE INDEX IF NOT EXISTS idx_reactions_stay ON reactions(stay_id);
CREATE INDEX IF NOT EXISTS idx_reactions_memo ON reactions(memo_id);
CREATE UNIQUE INDEX IF NOT EXISTS uq_reactions_stay_stamp ON reactions(user_id, stay_id, stamp) WHERE stamp IS NOT NULL AND stay_id IS NOT NULL;
CREATE UNIQUE INDEX IF NOT EXISTS uq_reactions_memo_stamp ON reactions(user_id, memo_id, stamp) WHERE stamp IS NOT NULL AND memo_id IS NOT NULL;
```

- 予定やメモが消えると反応も一緒に消える（外部キーの連鎖）。
- `users` に `reactions_seen_id INTEGER NOT NULL DEFAULT 0` を足す。ここまでの反応は既読という印。既存の DB には、`PRAGMA table_info` で確かめてから `ALTER TABLE` で足す（`pending_signups` と同じ作法）。
- 既存の予定の「元に戻す」（`/api/stays/restore`、`/api/memos/restore`）は同じ ID で入れ直すが、連鎖削除された反応は戻らない。許容する。

## スタンプ

ID と表示名は次のとおり。順序は画面の並びと同じ。

| ID | 表示名 |
|---|---|
| like | いいね |
| angry | おこ |
| sad | かなしい |
| thanks | ありがとう |
| otsu | おつかれ |
| laugh | わらい |

- 同じスタンプは、1 人が 1 つの対象に 1 回だけ（部分一意索引で保証する）。もう一度押すと取り消す。
- ID の一覧はサーバーの定数（`lib/stamps.js`）とクライアントの両方に持ち、テストで一致を確かめる。サーバーは一覧にない ID を 400 で拒否する。
- 画像は `public/stamps/<id>.png`。クライアントは画像を読み込もうとし、失敗したら内蔵の SVG イラストに切り替える。このため、画像がなくても動く。画像の仕様（サイズ、背景透過、絵柄の方向）と生成用の指示文は `docs/stamps.md` にまとめる。

## コメント

- 本文は前後の空白を除いて 1 字以上 40 字以下（コードポイント数）。改行と制御文字は空白 1 つにまとめる。
- 1 人が 1 つの対象に付けられるのは 5 件まで（超えたら 400 `この予定へのコメントは5件までです`）。
- 編集はできない。消して付け直す。
- 本文は常に `textContent` で描画する。HTML としては解釈しない。

## 書き込みの上限

- 1 ユーザーあたり、反応の追加と削除を合わせて 1 分間に 30 回まで。超えたら 429 `少し待ってからやり直してください`。
- 窓の長さは時計を差し替えられる作りにして、テストで確かめる（`test/fake-clock.js` の既存の仕組みを使う）。

## API

すべて合言葉の関門の内側にある。書き込みはログイン必須。

| メソッド・パス | 内容 |
|---|---|
| `GET /api/reactions/summary?from=&to=` | 期間内の予定・メモごとの要約。`{stays:{<id>:{stamps:{like:2},mine:["like"],comments:1}}, memos:{…}}`。反応のない対象は含めない |
| `GET /api/reactions/:type/:id` | 1 つの対象の全反応。`type` は `stay` か `memo`。`[{id,kind,stamp,body,created_at,user:{person_id,name,color},mine,deletable}]（`deletable` は `mine` と同じ）` を古い順で返す |
| `POST /api/reactions` | `{type,id,stamp}` でスタンプを付ける（すでにあれば 200 でそのまま）。`{type,id,body}` でコメントを付ける。付けたあとの 1 件を返す |
| `DELETE /api/reactions/:id` | した本人だけが削除できる |
| `GET /api/notifications` | 自分の予定・メモへの反応を新しい順に 50 件。`{unread, items:[{id,kind,stamp,body,created_at,from:{name,color},target:{type,id,date,label}}]}` |
| `POST /api/notifications/seen` | `reactions_seen_id` を、自分宛ての反応の最大 ID に進める |

- 通知の対象は「持ち主の `person_id` が自分の `person_id` と同じ予定とメモ」への、自分以外の人の反応。部屋のメモと持ち主のいない人の予定は対象外。
- `unread` は、`reactions_seen_id` より大きい ID の件数。
- `target.date` は、予定・メモの開始日（`YYYY-MM-DD`）。`label` は、予定ならその人の名前と期間、メモなら題名。
- 存在しない対象は 404、型や ID が不正なら 400。
- 反応の本文とスタンプ ID は、サーバー側で必ず検証する。

## 画面

### ダイアログの反応欄

予定（在室）とメモの編集ダイアログの下に「反応」欄を足す。

- 6 つのスタンプボタン。自分が付けたものは押された状態で見せる。ボタンの横に数を出す。
- 自分の予定・メモでは、スタンプボタンとコメント入力を隠す（これまでの反応の一覧は見られる）。
- コメント入力（40 字、残り字数つき）と送信ボタン。
- これまでの反応を古い順の一覧で出す。各行に、付けた人の色の丸、名前、スタンプまたはコメント、削除ボタン（`deletable` のときだけ）。
- 閲覧だけの人は一覧だけ。操作部分は出さず、「反応するにはログインしてください」と案内する。

### カレンダー上の表示

- 月表示の予定の右下に、反応の合計（スタンプ + コメント）を小さな数字つきの吹き出しアイコンで出す。0 件なら出さない。
- 週・日表示では、予定の中に同じものを出す。印刷では出さない。
- 要約は、カレンダーの予定を読み込むたびに同じ期間で取り直す。

### 新着の吹き出しと音

- 新着は、通知の取得（下記）で、これまでに見せた最大の反応 ID より大きい自分宛ての反応を指す。
- 該当する予定が今の画面に見えていれば、その上にあつ森風の丸い吹き出しを「ぽこっ」と出し、3 秒で消す。吹き出しにはスタンプの画像か、コメントの本文を出す。見えていなければ、ベルの数だけを増やす。
- ページを開いた直後の最初の取得では、まだ見ていない（未読の）反応のうち、この端末でまだ見せていないものを、新しい方から最大 5 件、予定のところに吹き出しで順に出し、音を 1 回鳴らす。これが「次にログインしたとき（開き直したとき）に、予定のところから反応が出てくる」にあたる。見せた最大の反応 ID は、ユーザーごとに `localStorage` に覚え、同じ端末で開き直しても同じ反応を繰り返し出さない（保存できない環境では、開くたびに出る）。未読の数（ベルのバッジ）は、ベルを開くまで残る。
- 予定がまだ描かれていないことがあるので、吹き出しは予定が描かれるまで最大約 6 秒待つ。画面の外や別の月にある予定には出さない（ベルの数だけ増える）。
- 音は、ブラウザが操作前の再生を止めているときは、最初の操作（押す・キー）のあとに鳴らす。
- 音は約1秒の「ぽーん」（上がり調子のあと、余韻がやわらかく消える）で、音声ファイル `public/sounds/pop.wav`を `Audio` で鳴らす。ファイルは `scripts/make-pop-sound.js` で作れ、同じ名前の別の音声で置き換えられる。新着が複数あっても、1 回の取得につき 1 回だけ鳴らす。
- ブラウザが操作前の自動再生を止めるので、ページを開いてから最初の操作より前の通知では鳴らない。鳴らせないときは何も言わずに無音にする。
- ミュートの切り替えはベルのパネルの中に置く。初期値は「音あり」で、選択は `localStorage` に覚える（読み書きは `try/catch` で囲む。使えなくても動く）。

### ベルと履歴

- 右上のログインボタンの隣にベルのボタンを置く。ログイン中だけ出す。未読数が 1 以上なら、数字のバッジを出す（99 を超えたら `99+`）。
- 押すと、履歴のパネルが開く。新しい順に最大 50 件、各行は「名前 + スタンプまたはコメント + 相対時刻 + 対象のラベル」。未読は強調する。
- 行を押すと、その日にカレンダーを移動し、パネルを閉じる。
- パネルを開いた時点で `POST /api/notifications/seen` を呼び、バッジを消す。
- Esc とパネル外のクリックで閉じる。キーボードで操作できる（フォーカスを移し、閉じたらボタンに戻す）。
- 電話の幅でもはみ出さない。パネルは画面の左右 16px 内に収める。

### 更新

- ログイン中は、30 秒ごとと、タブが見える状態に戻ったときに、`GET /api/notifications` を呼ぶ。タブが隠れている間は呼ばない。
- 反応を付けた直後は、その対象の欄と要約を取り直す。
- 他の人の反応が見えるのは、最長で約 30 秒遅れる。許容する。

## エラー処理

- 通信に失敗したら、反応欄の中に短い赤字を出す。送信ボタンは押し直せる。
- 429 は上の文言を出す。401 は既存の「ログインが必要です」の流れに乗せる。
- 対象がもう消えていた（404）ときは、欄を閉じて予定を取り直す。
- 通知の取得に失敗しても、画面は壊さず、次の周期で再試行する。

## 変更するファイル

- 新規: `lib/reactions.js`（API と検証）、`lib/stamps.js`（スタンプ定数）、`public/reactions.js`（反応欄・ベル・吹き出し・音）、`public/stamps/`（画像置き場。最初は `.gitkeep` だけ）、`docs/stamps.md`。
- 変更: `lib/db.js`（表と列）、`server.js`（ルート登録）、`public/index.html`（ベルとパネル）、`public/app.js`（要約の取得と、予定への反応数の描画の呼び出し）、`public/style.css`、`lib/auth.js`（退会は外部キーの連鎖に任せるため、基本は変更なし。テストで確かめる）、`README.md`、`docs/superpowers/specs/2026-11-06-user-accounts-design.md` の末尾に本書への参照。

## テスト

- API（`node:test`）: スタンプの付け外し、重複しないこと、不明なスタンプ ID、コメントの長さ・件数・空白の整理、自分の対象への反応の拒否、部屋のメモへの反応、持ち主のいない人の予定への反応、削除の権限（本人だけ。持ち主・第三者は 403）、未ログイン、書き込み上限、要約の形、通知の対象と並びと上限 50、既読の進み方、他人の既読に影響しないこと、予定とメモを消したときの連鎖削除、退会で自分の反応が消えること、既存 DB への列の追加。
- 画面の突き合わせ: `public/reactions.js` が触る要素の ID が `index.html` にあること、クライアントとサーバーのスタンプ ID が一致すること（`account.js` の既存テストと同じやり方）。
- 実ブラウザ（Playwright）: 2 人のログインで、スタンプとコメントを付ける、吹き出しが出る、ベルの数が増える、履歴を開くと既読になる、行を押すと日付へ移動する、ミュート、削除、電話の幅でのはみ出しがないこと。スクリーンショットで目視する。

## 検証の限界

- 音が実際に鳴るかは、自動テストでは確かめられない。再生の呼び出しが例外なく動くこと、ミュート時に呼ばれないこと、操作前に再生が拒否されたあと最初の操作で鳴ること（実ブラウザ）だけを確かめる。
- 実機の iPhone・Android では確認できない。デバイスのエミュレーションまで。

## 未解決の判断

なし。スタンプの絵柄は、画像が用意できるまで内蔵イラストで代用する。
